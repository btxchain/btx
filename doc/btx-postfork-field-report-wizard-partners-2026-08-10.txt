BTX v0.33.2 Post-Fork Field Report
MatMul v4.7 activation (height 185,000) — independent operator evidence
Wizard Partners mining operation · ~35 sm_120 nodes + archive infrastructure · 10 Aug 2026, ~18:00 UTC
1. Executive summary
The v0.33.2 binary and sm_120 hardware validate the canonical v4 chain correctly. Confirmed on a fresh, fully independent node (RTX PRO 6000 Blackwell, CUDA 13.2 runtime, peered only to project seeds, no contact with our fleet): fed the canonical chain via submitblock, every block from 185,000 onward validates OK at ~5s/block.
The systemic bottleneck is P2P delivery of v4 block data, not validation. Headers propagate normally (we track the mining edge in real time); block data does not. Nodes relay only what they have validated, so data propagates hop-by-hop at global validation speed while the mining edge extends faster — leaving most of the network permanently behind.
Practical consequence: any node that cannot obtain block data out-of-band stalls at the fork edge, no matter how capable. A fresh independent node with only official seeds stalled at 184,999 waiting for 185,000+ data — the same wall our whole fleet hit.
We recovered autonomously and are contributing back: an internal raw-block feeder brought 30+ nodes onto the canonical chain, and our public archive node now serves full canonical v4 data to the network (details in §5).
2. Timeline of our observations (UTC)
Aug 9, evening — full fleet migrated to v0.33.2 native mining ahead of the fork (two-gate verification: GPG fingerprint 0804 EB10 … 525F 4099 + per-asset SHA256; canary node soak-tested).
Aug 10, 02:26 — activation at 185,000. Our island (one bridge attestation authority + fleet) followed a local 185,004 and separated from the network at ~185,003. All nodes saw canonical headers climb but could not connect canonical blocks.
Morning — diagnosis: “ExactReplay: cancelled” (outcome=3) on every canonical block. Root cause: the asynchronous RC replay of a non-active branch is preempted. Setting matmulrcexecution=strict-device (synchronous replay) + invalidating the local stub lets the node validate and connect the canonical chain.
Afternoon — 30+ nodes recovered onto canonical via strict-device + backbone addnodes + internal block feeder. A fresh independent node (project seeds only) reproduced the delivery stall, isolating the bottleneck to P2P data distribution.
3. Key technical findings
3.1 strict-device unblocks preempted replay
Default asynchronous RC replay of a non-active branch gets preempted (“ExactReplay: cancelled”, outcome=3) and the node never connects the competing (canonical) branch — this is very likely the “zombie block” freeze reported on Aug 10. Synchronous strict-device replay with a free GPU validates the same blocks without issue (~4.5–5s/block on RTX 5090 / PRO 6000).
matmulrcexecution=strict-device   # + invalidateblock <local stub> → node reorgs to canonical
3.2 RC authority qualification is bound to the exact software stack, not just silicon
Golden manifest in v0.33.2 covers sm_120 and M4-class only — Ada (4090), Hopper (H100) and, per community reports, B200/B300 (sm_100/sm_103) cannot self-qualify. Consistent with the MXFP4-native requirement.
On legitimate sm_120 silicon, CUDA runtime 13.0 / cuBLASLt 13.1 produces episode_digest_mismatch_backend_vs_cpu; CUDA 13.2 / cuBLASLt 13.4 passes the production canary. Worth documenting the exact supported runtime versions for archive operators.
3.3 P2P v4 block delivery is the systemic bottleneck
Headers propagate at network speed; block data lags hours behind the mining edge (~0.5 blocks/min observed via getblockfrompeer against seed/backbone peers, vs ~12 blocks/min local validation capacity per node).
getblockfrompeer requests are accepted ({}) but blocks frequently never materialize (ReadRawBlock: OpenBlockFile failed nFile=-1) — peers appear to have headers but not data, or rate-limit block serving.
Public explorers’ validated tips trail the mining edge by dozens of blocks — whoever mines the current edge is effectively self-feeding, while the rest of the network cannot obtain data fast enough to follow, let alone mine.
4. Recovery method (reproducible, in case it helps other operators)
1. Add matmulrcexecution=strict-device and restart (mining paused; GPU free for replay).
2. invalidateblock the local stale branch tip so the canonical branch becomes eligible.
3. Feed raw canonical blocks in parent-first order via submitblock (sourced from any node that already has the data — RPC getblock verbosity 0). Validation proceeds at full GPU speed, independent of P2P.
4. Once at tip, normal P2P announce/push keeps the node current.

6. One ask
The single unblock for us (and likely every stalled operator): the IP of a node that actually holds the newest v4 block data — the miner currently extending the tip, or the explorer backend — so we can addnode it directly. Headers reach us fine; block data for the newest ~50 blocks has no source among seeds or discovered peers. With one direct peer we validate at ~12 blocks/min and close the gap in minutes. Alternatively, a REST /rest/block endpoint on any seed achieves the same. We are happy to mirror, test, or help operate either.
