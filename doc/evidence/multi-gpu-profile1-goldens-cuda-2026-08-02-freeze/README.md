## Why this still does not seal the cohort

The committed Metal corpus is bound to a different revision, so the two halves
do not share a `source_tree_fingerprint`. Under the equivalence rule in
`doc/btx-matmul-v4.7-production-golden-policy.md` a cohort is admissible only
when both providers reproduce **the same** build-relevant tree, and the C++
comparator enforces exactly that (`RCProductionGoldenManifestCohortValid`
requires equal `source_revision` and `source_tree_fingerprint` across entries).
Digest equality alone is not the gate.

This is a churn problem, not a correctness problem: every consensus fix that
touches `src/` invalidates whichever corpus was recorded first. The way out is
to stop landing `src/` changes, then run **both** providers once against that
final tree. Regenerating CUDA takes about five minutes of GPU time; the binding
constraint is Metal hardware availability.

`CommittedRCProductionGoldenManifest()` therefore stays empty, and public
heights and both ratification flags stay fail-closed.
